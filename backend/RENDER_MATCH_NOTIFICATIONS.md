# Telegram match notification worker on Render

Create a **Background Worker** service from this repository. Set its root directory to `backend`, build command to `npm install`, and start command to `npm run start:match-notifications`. Set the same `MONGODB_URI`, `TELEGRAM_BOT_TOKEN`, and `TELEGRAM_CHAT_ID` values used by the API web service, plus `CRICKET_API_KEY` for CricAPI synchronization. Never commit those values.

The worker must use an always-on paid Background Worker instance. A Render Cron Job is not suitable for continuous one-minute polling, and a sleeping free web service cannot guarantee match notifications. Keep exactly one worker instance; MongoDB's unique announcement-key index still prevents duplicate messages if instances overlap during a deployment.

### Contest matchmaking queue index

Both the API and Background Worker run the guarded `activeQueueKey_1` index initialization before normal contest index creation. The canonical index is unique on `{ activeQueueKey: 1 }` and partial on string values only. The field is assigned a string while a contest is in the matchmaking queue and removed with `$unset` when it leaves the queue. This replaces the legacy unique sparse index, which conflicted with the schema's string-only partial index.

On startup, initialization checks for duplicate string keys before replacing the known legacy sparse index. If duplicates exist, startup stops and reports example keys without changing documents or dropping the index. Resolve those queue collisions manually in staging/production data, then restart. Unknown index definitions are left untouched and cause a clear startup error. No documents or collections are deleted. For a manual preflight, run an aggregation on `contests`: match `activeQueueKey` with `$type: "string"`, group by `activeQueueKey`, and filter groups with count greater than one. The API and worker must run the same code revision during rollout.

Optional settings:

- `MATCH_NOTIFICATION_INTERVAL_MS` (default `60000`; minimum effective value 15000)
- `MATCH_NOTIFICATION_LEAD_MINUTES` (default `60`; upcoming reminders are sent during this lead window)

The worker scans published `Match` records and refreshes the CricAPI feed every 15 minutes. CricAPI matches are upserted into MongoDB by provider ID as unpublished admin-review records; only creating an admin contest publishes an imported match to the user match list and freezes its admin-approved teams, format, and schedule. Provider scores, status, match state, and provider last-sync time continue to refresh. The sync path detects CricAPI live transitions, confirmed `ms=result` final results, and important provider status or schedule changes, but queues notifications only for matches already published by an admin. Test match stumps/day updates are status notices, never final results. Provider final-result messages include available scores and winner text when the provider supplies it.

Feed synchronization does not update manual match status, results, contests, participants, wallet records, or settlement fields. It does not infer completion from elapsed time or use provider statuses to settle contests. Existing admin-confirmed `live`, `completed`, `cancelled`, and `abandoned` states and upcoming reminders/reschedules continue to be handled by the same Telegram scheduler. The current project does not define a separate `postponed` status. Match timestamps are stored as MongoDB dates (UTC instants); CricAPI's `dateTimeGMT` is parsed as UTC even when the provider omits a `Z`, and displayed times use `Asia/Kolkata` (IST).

Provider notification events are written to the unique-key `TelegramAnnouncement` collection before provider sync state is advanced. `PENDING` and retryable `FAILED` records are recovered by the existing worker scan after restarts. MongoDB atomic reservation prevents two worker instances from claiming the same event concurrently. Telegram API rejections use a persisted retry delay (at least 60 seconds); a network timeout can occur after Telegram accepted a message, so such deliveries are recorded as `UNKNOWN` and not automatically retried to avoid duplicate channel posts.

The same existing worker polling loop also closes contest entries. Contest `expiresAt` is the configured entry cutoff (currently created from the match start time); closure uses the earlier of that cutoff and the actual match start. A confirmed CricAPI `live` or `result` state closes published-match contests immediately, including when the provider reports a match starting early. Provider postponement/delay text defers scheduled closure until an updated admin schedule is available. Missing schedules are skipped unless a live/result state or admin match status confirms the match has started. Closure sets `Contest.entryClosedAt` atomically and leaves participants, contest status, wallet data, and settlement fields untouched. The join API also checks provider state and atomically excludes contests whose entry closure marker is set. No additional Render service or environment variable is required.

The same polling loop reads synchronized `providerState=result` data and persists contest outcomes only for admin-published matches and closed, eligible head-to-head contests. A provider team name must map exactly to an admin-approved match side; ambiguous mappings are recorded as `AMBIGUOUS`, and later provider updates can resolve them. Confirmed ties, no-results, and abandoned matches are recorded without a contest winner. Stumps/day updates, postponed matches, and non-final statuses do not produce outcomes. The recorded provider outcome and determined participant are separate from `winnerId`, wallet records, platform fees, and settlement fields; this phase does not pay prizes or refund entries.

## Provider outcome settlement

The same Background Worker loop settles only persisted `DETERMINED` provider winners for published CricAPI matches and closed, full/locked head-to-head contests with two opposing paid/free entries. It uses the contest's stored `winnerPayout`, `platformFee`, and fee percentage (currently 10%); inconsistent stored amounts are skipped for review. Ties, no-results, abandoned matches, ambiguous outcomes, and contests without a confirmed winner are not paid or refunded.

Each payout, `CONTEST_WINNING` wallet transaction, optional platform-fee ledger entry, and contest `winnerId`/`SETTLED` fields commit in one MongoDB transaction. The worker claims a contest atomically and uses stable transaction and ledger references, so retries and concurrent instances cannot pay twice. If a transaction aborts or the worker stops mid-settlement, MongoDB rolls back every financial write and the next worker check retries it. Existing result correction or refund flows are not invoked by this provider settlement path.

MongoDB must support multi-document transactions. MongoDB Atlas clusters satisfy this through replica sets; a standalone local MongoDB server does not. The worker creates the existing Contest, Wallet, WalletTransaction, and PlatformLedgerEntry indexes before starting its polling loops. No additional environment variables or Render services are needed. Deploy the API and the existing always-on Background Worker from the same code revision; retain one worker instance for simpler operations (the database claim remains safe during overlaps).

For production verification, first use a staging Atlas database and a published provider match with one closed contest, two opposing paid entries, and a persisted `DETERMINED` provider outcome. Confirm one completed `CONTEST_WINNING` transaction, one platform fee record when the fee is nonzero, wallet before/after values, and contest `winnerId` plus `settlementStatus=SETTLED`. Wait through multiple worker polls and restart the worker; verify these counts and balances remain unchanged. For production, choose a low-value contest and monitor the worker logs and those same MongoDB records after the deployment. Do not edit balances or settlement records manually as part of verification.

## Automatic contest refunds

The existing worker also refunds paid entries after a one-player contest reaches its configured `expiresAt` cutoff. It refunds match contests only for an explicit manual cancelled/abandoned/tie/no-result state or a persisted Phase 4 CricAPI `ABANDONED`, `TIE`, or `NO_RESULT` outcome. A missing, delayed, or ambiguous result alone is not a refund reason. Already settled or already refunded entries are excluded. Refund reasons use the existing `cancellationReason` values (`NO_OPPONENT`, `MATCH_CANCELLED`, `MATCH_ABANDONED`, `MATCH_NO_RESULT`).

Each paid entry's wallet balance increment, `CONTEST_REFUND` transaction, participant refund fields, and contest settlement status commit in one MongoDB transaction. Stable references are shared with the existing refund path, and the contest update is conditional, so repeated worker scans, restarts, and concurrent workers cannot double-credit. Refund notifications are sent through the existing notification service after commit. A per-participant notification status lets the worker retry delivery after a restart; the notification reference is idempotent. Existing winner payouts and platform fee ledger entries are not modified.

This uses the existing Background Worker and MongoDB transaction requirement above. No new Render service or environment variable is required. The worker creates the existing Notification index before polling. Before production rollout, review eligible historical one-player contests past `expiresAt` and any contests left in `REFUND_REQUIRED`/`REFUND_PROCESSING`; the first worker check will resume their refunds. For staging, use an Atlas replica-set database and test (a) one paid entrant after `expiresAt`, (b) two paid entrants on an explicitly cancelled/abandoned/no-result match, and (c) a provider tie/no-result/abandoned contest after Phase 4 persists the outcome. Verify the matching `CONTEST_REFUND` transaction for each paid player, wallet balance snapshots, `refundStatus=COMPLETED`, the contest reason and `settlementStatus=REFUNDED`, and one `REFUND_COMPLETED` notification. Repeat worker polls and restart the worker; balances and transaction counts should stay unchanged. Also check that ambiguous or missing results and already-settled contests receive no refund. Use staging first, then verify a low-value eligible contest in production while monitoring worker logs and MongoDB records.

Telegram Bot API rejections are recorded as `FAILED` and retried on the next worker scan. A network timeout can occur after Telegram accepted a message, so such deliveries are recorded as `UNKNOWN` and not automatically retried; this avoids duplicate channel posts. Inspect `TelegramAnnouncement` records with `UNKNOWN` status and check the channel before manually resolving one.
